# 0009: People sign in with server-side sessions; keys stay for machines

Status: accepted (2026-11-16)

> **Since built:** the web UI ([`packages/web`](../../packages/web/README.md)) and the OAuth authorization server for remote MCP ([ADR 0010](0010-oauth-for-mcp.md)) both exist now and use the sessions described here. Where this record says "later" or "not built" for them, read it as history. How people sign in today, including the first owner's path with a server-printed link, is in [`docs/sign-in.md`](../sign-in.md).

## Context

Everything authenticated with API keys. A web UI (later) and an OAuth consent screen for remote MCP (next) need people to sign in from a browser. The ground rules are: four ways to sign in (an email code or link, optional single sign-on through any OpenID Connect provider, email and password, and a one-time link printed by a server command); invite only, so only existing active members sign in; no tokens in the browser, so sessions live on the server behind an HttpOnly cookie on the API's origin; keys unchanged. The code will later run a hosted service that has to pass a SOC 2 audit, so every authentication event is audited, deprovisioning ends access at once, and nothing sensitive is stored in the clear.

Two facts of the existing design shape the rest. Members are rows per workspace (`users` is unique on tenant and email), so one person can be several members. And every tenant table has forced row-level security whose policy raises when no tenant is set, and the app connects as a role that can't bypass it.

## Decision

**Sessions are rows in Postgres.** A `sessions` table, tenant-scoped with forced RLS, holds the SHA-256 of a 256-bit random token, the member, how they signed in, when, idle and absolute expiry, a bounded user agent and client address, and when and why it was revoked. The cookie holds the token, nothing else. Like `api_keys.key_lookup`, a select-only `session_lookup` policy lets a request read the one row whose token hash it presents before the tenant is known, then the tenant is set and everything else is normal. A row can be revoked on the spot, listed for an access review and deleted after it ends, which a signed token can't do. The cost is one indexed lookup per request, the same as a key.

**A session resolves to the same context a key does.** The member's role, object and field rules are read on every request through the same code as keys (`keyOwner`, `memberAccess`), so a role change or disabling takes effect on the next request. The context carries `session` (ID, sign-in time, method) and no key ID, and its surface is `web` (a new value in the audit log's CHECK). The audit row's hashed columns are fixed, so the session ID goes in `details.session`; `audit()` adds it whenever a session is acting.

**Sessions are not scope-narrowed.** A key's scopes exist to make a credential smaller than its owner, for a dashboard or an agent. A person in a browser is the owner, acting with their whole role, so a session holds every scope the role can use. Two places used to read the caller's scopes as a ceiling: creating a key (a key can't mint a broader key) now reads, for a session, "only scopes your own role can use", which together with the existing rules for keys:manage is the same ceiling a full-scope key would have; the admin MCP surface check never sees a session.

**The cookie wins only when there is no Authorization header.** Any `Authorization` header makes the request a key request, valid or not, and the cookie is ignored. That keeps the two credential paths separate and makes mixed requests predictable.

**Finding a person's memberships across workspaces.** Signing in starts before any workspace is known, and the email (or the provider's subject) can match members in several. The lookup must not weaken RLS for `users` (its policy raises without a tenant, which is what catches queries that forget one) and must not use a privileged connection. So a small table, `sign_in_identities`, maps an email in its canonical form, or an OIDC issuer and subject, to (workspace, member) pairs. Triggers keep it in step with `users.email`, with disabling (a disabled member has no email identity) and with the SSO link, and the migration fills it for existing members tenant by tenant. Its `identity_lookup` policy is select-only and matches only rows whose kind and value equal what the transaction set in `app.identity_lookup`: a request learns the memberships of the one identity it names, nothing else, and sees nothing without naming one. Status, names, roles and password hashes are then read inside each workspace under the normal policy, one transaction per workspace, at most 20: members stored with exactly the typed address first, then by workspace. When there are more, nothing is dropped silently: the choice says so and the person can name the workspace (`workspace`, `ws_…`, on every sign-in request), which looks in that one only.

**One canonical email form, and a code proves one address.** The database's `lower()` and JavaScript's `toLowerCase()` fold some non-ASCII letters into ASCII ones (the Kelvin sign into `k`, `İ` into `i`), differently from each other and depending on the database locale, so two different mailboxes could match one member. Sign-in therefore matches emails in one canonical form, computed identically in SQL (`app.canonical_email`, using the "C" collation) and in the server: surrounding whitespace trimmed and only `A`–`Z` lowercased. New member emails must be printable ASCII without spaces or control characters (internationalized addresses aren't supported yet); older rows keep working by their canonical form. Matching is not proof, though: an emailed code proves control of the address it was sent to, so each message goes to an address exactly as stored and signs in only the memberships stored with exactly that address. When one typed address matches several stored spellings, each spelling gets its own message, flow and code (at most three, the typed spelling first), and audit entries go only to the workspaces a message was sent for. Otherwise an admin who added a case variant of someone's address to their own workspace would receive a code that signs in to the other person's workspace. A password proves the one membership it matches. Sign-in steps that span workspaces (`sign_in_flows`) have no tenant; their policy shows only the rows whose browser-cookie hash or link-token hash the transaction presents, plus already-expired rows to the cleanup job.

**One workspace per session.** With several memberships, the sign-in returns a workspace choice: workspace names and IDs only, bound to a new pre-session cookie, single-use, 5 minutes. It is shown only after the identity is proven, so it reveals nothing to someone who hasn't.

**CSRF: an HMAC-bound token plus Origin checks.** Cookie-authenticated requests that change state must carry `X-CSRF-Token` equal to HMAC(server key, session ID), have `Origin` equal to `PUBLIC_URL` (missing or `null` is refused), and, when the browser sends `Sec-Fetch-Site`, have it be `same-origin`. The token is bound to the session without storing anything, can't be computed from what the database holds, and is only handed out in same-origin responses. A naive double-submit cookie was not used: a cookie set by a sibling host could defeat it, and the token would have to be readable by script anyway. SameSite=Lax is a layer, not the control. The built-in pages' own forms can't send a header, so those three forms (sign out, set and remove a password) carry the same token as a field with the same Origin checks. The sign-in endpoints, which have no session yet, check Origin and Sec-Fetch-Site so no other site can sign a browser in.

**Cookies.** `__Host-hlcrm_session` with `Secure; HttpOnly; SameSite=Lax; Path=/` and no Domain, so only this exact https host can set or read it. Lax rather than Strict so that the email link and the provider's redirect, both top-level navigations from elsewhere, carry the pre-session cookie. For local development on `http://localhost` the names lose the prefix and `Secure`; any other http origin is refused at startup.

**Every single-use secret is hashed and short-lived.** Pre-session cookies, link tokens and session tokens are 256-bit random and stored as SHA-256. Email codes are 8 digits (five attempts, so a guess succeeds about once in 20 million), stored as an HMAC under a key derived from the master key, so a copy of the database alone can't brute-force them. OIDC `state`, `nonce` and the PKCE verifier are HMACs of the pre-session cookie, so nothing about them is stored at all.

**The emailed link must be opened in the browser that asked for it.** Safer than a link that works anywhere: an intercepted or forwarded email doesn't sign anyone in, and a mail scanner that fetches the link can't use it (opening it shows a Continue button). Someone reading mail on another device types the code instead. The server-printed link is the exception: it is delivered out of band by an operator, so it can't be bound to a browser, and it lives 15 minutes instead of 10. Invitations carry no credential at all: they point at the sign-in page.

**Passwords.** argon2id from Node's own `crypto.argon2` (added in Node 24.7.0; it also needs OpenSSL 3.2 or later, which Node bundles) at OWASP's minimum of 19 MiB, 2 passes and 1 lane, with a 16-byte salt and a 32-byte hash, stored as a self-describing string so parameters can be raised later with rehash-on-sign-in. If argon2 isn't available at runtime (a Node built against an older shared OpenSSL), scrypt with OWASP's parameters (N=2^17, r=8, p=1) is used, in the same format. Hashing runs on libuv's thread pool, at most four at once with 64 waiting, so sign-in can't exhaust memory. An email with no usable password still costs one hash. Rules are length (12 to 256), a strength estimate, and not containing the email's local part or the workspace name; no composition rules. The estimate is zxcvbn-ts with its common and English dictionaries, which ship inside the package, so it works offline; the email and workspace name are added as words to try, and a password rated below 3 of 4 (roughly under 10^8 guesses) is refused. It recognises common passwords, words, names, dates, keyboard runs, repeats and l33t spellings, rather than matching a fixed list. Only the first 256 UTF-16 code units are estimated, so a check takes a few milliseconds. The email and workspace-name checks stay alongside it because a long password containing either can still rate as strong, as can a run of only two distinct characters, which is also refused. A breached-password check (Have I Been Pwned, k-anonymity) is optional and off by default because it calls a third party. A member has no password until they set one after signing in another way, and a reset is the email code followed by setting a new one, so there is no reset token to steal. Changing a password needs the current one or a sign-in in the last 10 minutes, and ends the other sessions.

**Lockout locks only the password.** Five failures in a row lock that member's password sign-in for 1 minute, doubling to an hour. Email code, SSO and server links keep working and clear it. An attacker can keep a password locked, but not keep a person out. Each attempt is counted in the database before the hash is checked, and the fifth sets the lock at once (a right password clears it), so parallel guesses can't all be checked before the lock lands; this holds across processes and holds no transaction open while hashing. Wrong current-password guesses on a password change count toward the same lockout.

**No enumeration.** Every answer that could depend on whether an email belongs to someone is the same: same status, body and cookies. The membership lookup and email sending for a code request, and failure counting and audits, run after the response. Limits keyed by an email count whether or not it exists. Remaining: checking a password against several workspaces costs one hash each.

**Single sign-on on `jose`, not a full client library.** The server needs discovery, a code-for-token request and ID token verification: a few small functions. `jose` (MIT, no dependencies) verifies the signature, issuer, audience and expiry; the code checks the nonce, `azp`, `email_verified` and allowed domains. Every request to the provider goes through `lib/outbound.ts` (https, SSRF ranges, pinned DNS, timeouts, size limits), which a fetch option alone wouldn't guarantee. `openid-client` would have added two packages for the same result. The provider's subject is stored on first sign-in and preferred afterwards, so a changed email at the provider can't move a sign-in to another member; a member linked to one subject is never matched by email for another.

**SSO trusts the provider's email verification, so each workspace can opt out.** One provider serves the whole server, and a verified email links to matching members in every workspace that allows SSO. Each workspace's owner can turn SSO off (`sso: false`) or narrow it to email domains (`sso_allowed_domains`, within the server's `OIDC_ALLOWED_DOMAINS`) with `PATCH /v1/workspace/sign-in`, alongside the password switch. SSO is on by default, so a single-workspace self-hoster gets it by configuring the provider. Both lists and the switch are re-checked on every SSO sign-in, by subject too, against the email the provider reports now. A member can unlink themselves (from a session with a recent sign-in) and an admin can unlink a member under the same rules as revoking their sessions; both are audited. The sign-in page's CSP allows the SSO form to reach the authorization endpoint's origin as discovered, since browsers apply `form-action` to the redirect.

**Idempotency records belong to a credential.** `idempotency_keys.key_id` became `credential_id` with a `credential` kind (`key` or `session`). A session's retries replay within that session; the stored response stays encrypted, bound by AAD to the credential, and refused if the permission fingerprint changed.

**Sessions, keys and admins.** Ending your own session takes a session; an API key ends sessions only through `members:manage`, and a session it may not act on answers like an unknown one. Listing a member's sessions (with addresses and user agents) follows the same owner and permission-superset rules as revoking them. A key made from a session outlives it (sign-out, "revoke others", a password change and an admin's revoke leave it working), so creating or rotating a key from a session needs a sign-in in the last 10 minutes; keys are revoked separately and listed in the access review.

**Email budgets.** Sign-in email has a budget per workspace it is for and a generous server-wide ceiling as a last resort (logged as an error when hit); invitations have their own budgets per workspace and per sender, answered with 429. So neither one admin's invitations nor codes requested for one workspace's members can silence sign-in email for everyone. Names that other people chose (the workspace's, the inviter's) go into email as plain text with links defused.

**Routes say who they are for.** A route can be `credential: "session"` (the caller's own session and password: a key is refused) and `permission: "own_credential"` (any authenticated caller, even with no permissions, because it acts only on their own sign-in). The unauthenticated surface is one list in `api/auth-public.ts`, and a test asserts it.

**Pages are separate and replaceable.** `web/pages.ts` holds the templates, `web/handlers.ts` the page handlers, and the JSON endpoints serve both, so a later web UI can drop the pages and keep the endpoints. The pages use no script, one same-origin stylesheet, a strict Content-Security-Policy and `frame-ancestors 'none'`.

## Consequences

- People can sign in; keys work exactly as before. A key request with a cookie present is still a key request.
- Disabling a member ends their sessions and keys in one transaction. Role changes apply on the next request.
- The next task (an OAuth authorization server for remote MCP) can require a signed-in session on its consent page with `resolveSession` (`auth/sessions.ts`) or `ctx.session` on a `/v1` route, and a fresh sign-in with `requireRecentSignIn(ctx, seconds)`; `ctx.session.signedInAt` is when the person last proved who they are, since every sign-in starts a new session.
- New tables: `sessions`, `member_credentials`, `sign_in_identities`, `sign_in_flows`; `tenants.password_sign_in`, `sso_sign_in` and `sso_allowed_domains`; the function `app.canonical_email`; `idempotency_keys.credential_id` and `credential`; `web` in the audit surface CHECK. Migration 010 changes no existing data except to fill `sign_in_identities`.
- Limits are in memory per process, like the key limiters. Several API processes multiply them until a shared limiter exists.
- The audit log can't record attempts for an email that belongs to nobody (there is no workspace to put them in); they are rate limited, and SSO refusals are logged with a reason.

## Not built

- Multi-factor authentication (TOTP) and passkeys. Sessions record how they were created and when, so a later step-up can check both.
- The OAuth authorization server for remote MCP: built next, in [ADR 0010](0010-oauth-for-mcp.md) (since built).
- SCIM, self sign-up, workspace creation from the browser, and browser sign-in for the `crm` CLI. (The web UI was listed here too; it has since been built: see the note at the top.)
- A shared (cross-process) rate limiter.
- Internationalized email addresses.
